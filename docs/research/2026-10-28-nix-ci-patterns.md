# Existing Nix CI patterns

- **Question:** What do other people, including StepBro and Determinate Systems, do for Nix evaluation and CI that caboodle could learn from?
- **Researched:** 2026-10-28, normal
- **Context:** [CI redesign requirements](../prd/ci-redesign.md). No evaluations, builds or infrastructure changes ran during this research.

## Sub-questions

1. StepBro's own setup and Colmena evaluation strategies: answered, with no comparable resource measurements found in the inspected material.
2. The remembered Determinate evaluation action and related GitHub tools: mechanisms and real users checked; exact remembered tool remains a gap.
3. Established Nix CI evaluation and result reuse patterns: answered at the implementation-pattern level; compatibility and resource measurements remain explicit gaps.

## What this suggests for caboodle

The first comparison should preserve the monorepo, cross-host configuration
and Colmena deployment. Test explicit evaluator budgets and smaller batches
against the current full-manifest command, on one frozen revision, requiring
the same complete host-to-derivation mapping. Measure peak memory and total
CPU/time together: reducing peak memory can repeat shared work.

`nix-eval-jobs` is the common evaluator in several inspected systems.
`nix-fast-build` demonstrates a ready-made evaluation-to-build flow, but
consolidating builds into its orchestration would change the current per-host
CI job view. Direct use of nix-eval-jobs to supply the existing comparison
and build stages is also a candidate. Neither choice has been adopted.

Keep derivation reuse incremental. Hestia and Hydra establish that building
evaluated derivations is a real pattern; Atelier and a Hestia user's fallback
show that repeated evaluation can be a deliberate trade-off. First measure
whether bounded evaluation is sufficient, then compare the cost of repeated
evaluation against retaining and transporting its results. There is no
evidence yet that changing Colmena's deployment interface is necessary.

The existing shared store is useful for avoiding duplicate builds. Its
retention policy must deliberately cover derivations, sources and built
outputs needed after an ephemeral job exits. Persisting that state is
compatible with disposable job environments; fresh job state does not
require an empty build store.

Hestia's released transport is tied to GitHub Actions cache storage.
It is useful prior art, but not a configurable replacement for the current
cache. nixbot offers relevant evaluation, reuse and deployment mechanisms,
but its lifecycle and integration guarantees need testing before considering
it a replacement for the whole CI setup. An open-source repository's age or
activity alone does not establish production reliability.

No researched implementation, by its name alone, guarantees the combined
requirements for current-target evidence, scoped secrets, disposable job
state, exact derivation previews and halted rollout on failure. Those remain
integration checks against the design requirements.
